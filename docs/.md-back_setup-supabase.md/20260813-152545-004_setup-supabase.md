## 3.0 前提知識と、これから作るもの

### Supabaseとは

**PostgreSQL（Postgres）というデータベースを中心に、その周辺機能をまとめてホストしてくれるサービス**です。
自分でサーバーを借りてDBを立てる代わりに、Web画面から「project」を1つ作ると、
DB・ファイル置き場・APIサーバーが一式用意されます。

このリポジトリでは、Supabaseの機能のうち次の3つだけを使います。

| 機能 | 何をするものか | このリポジトリでの用途 |
| --- | --- | --- |
| **Database** | Postgresそのもの。表（table）にデータを入れる | 報告の内容・状態・監査ログを保存する |
| **Storage** | ファイル置き場。S3のようなもの。`bucket`という入れ物に分けて保存する | スクリーンショットとログのファイルを保存する |
| **Edge Functions** | 小さなサーバープログラム（TypeScript / Deno）をURLとして公開する仕組み | アプリとDBの間に立つ唯一の窓口 |

「Supabase project」は、これらがまとまった**1セット**を指します。
projectを作ると `https://<project-ref>.supabase.co` という固有のURLが割り当てられます。

### 用語ミニ辞典

この先で何度も出てくる言葉です。ここを読んでおけば、以降の説明で詰まらないはずです。

| 用語 | 意味 |
| --- | --- |
| **table** | はい、RDB（リレーショナルデータベース）の「表」です。行と列でデータを持ちます。このリポジトリでは4つ作ります |
| **migration** | 「この表を作る」というSQLを書いたファイル。DBの設計図であり、実行すると設計が反映される。`supabase/migrations/*.sql` がそれ |
| **RLS** | **Row Level Security**（行レベルセキュリティ）の略。Postgresの機能で、「誰がどの行を読み書きしてよいか」を行単位で制御する。RLSを有効にすると、**許可（policy）を明示的に書かない限り一切アクセスできなくなる** |
| **policy** | RLSの下で「この条件を満たす行なら読んでよい」と許可を与えるルール。このリポジトリでは**あえて1つも作りません**（後述） |
| **anon key / publishable key** | クライアントアプリに配ってよい公開鍵。「匿名（anonymous）ユーザーとしてAPIを呼びます」という身分証。**これ自体には強い権限がなく**、RLSとpolicyで守られている範囲しか触れない。新しい名前が `publishable key`（`sb_publishable_...`）、古い名前が `anon key`。同じ役割です |
| **service role key** | すべてのRLSを無視できる管理者鍵。**絶対にアプリへ配布しない**。サーバー側（Edge Functions）だけが持つ |
| **bucket** | Storage内のファイル置き場の単位。`private` にすると、URLを知っていても直接ダウンロードできない |
| **署名付きURL（signed URL）** | 「この1ファイルを、この操作だけ、この秒数だけ許可する」という使い捨てURL。privateなbucketのファイルを一時的にやり取りするために発行する |
| **Edge Function** | 上記の通り、URLで呼べる小さなサーバープログラム。`https://<ref>.supabase.co/functions/v1/<関数名>` で公開される |
| **CLI** | `supabase` コマンド。migrationの適用やfunctionsのdeployをターミナルから行う |
| **dispatcher** | このリポジトリ側の常駐プログラム。GitHub Issueを見て、コーディングAgentを起動する側。Supabaseの一部ではありません |
| **Agent** | Issueの内容を読んでコードを書き、branchへpushしてdraft PRを作る自動化されたコーディングAI（`codex` / `claude`）。dispatcherがこれを起動します |

### このリポジトリがSupabaseに作るもの

`supabase/`配下は次の3つで構成されています。作業前に「何が作られるのか」を把握しておくと、
権限やsecretsの意味が分かりやすくなります。

#### ① DB（`migrations/202608110001_initial.sql`）

| object | 役割 |
| --- | --- |
| table `reports` | 報告本体。status、artifactの記述、GitHub Issue番号、`expires_at`（既定30日） |
| table `agent_runs` | Agentの実行1回分の記録。**1 reportにつき同時1 run**をunique indexで強制 |
| table `report_events` | 追記専用（append-only）の監査event。「いつ誰が何をしたか」の履歴 |
| table `report_rate_limits` | 1時間あたりの受付回数のカウンタ |
| function `claim_agent_run` | 排他claim（`service_role`のみ実行可） |
| function `consume_report_rate_limit` | rate limitを1回分消費する（既定10回/時） |
| function `recover_stale_agent_runs` | 45分以上放置されたrunを`timed_out`へ回収 |
| bucket `user-reports` | **private**、10MiB上限、png/ndjson/jsonのみ |

**「claim」とは**: 「この報告は自分が担当します」という**取得予約**のことです。
dispatcherが複数動いていたり、同じIssueを二度拾ったりすると、同じ報告に対してAgentが2つ走ってしまいます。
そこで `claim_agent_run` がDB上で「担当を1つだけ確保する」処理を行い、
`one_active_run_per_report` というunique indexが**進行中のrunを1 reportにつき1件しか存在させません**。
2つ目のclaimは必ず失敗します。

**「rate limit消費」とは**: 「1時間に10回まで」という上限に対して、
1回受け付けるたびにカウンタを+1することです。11回目は `429 rate_limited` で拒否されます。
`consume_report_rate_limit` は「+1してから、上限内かどうかを返す」関数で、
カウンタの読み取りと更新が1回のSQLで完結するため、同時アクセスでも数え漏れが起きません。

**「45分以上claimed」とは**: Agentが担当を確保（claim）したまま、
プロセスが落ちるなどして終了報告を返さないケースのことです。
その報告はいつまでも「実行中」のまま固まり、誰も再実行できません。
`recover_stale_agent_runs` は「claimしてから45分たっても終わっていないrun」を強制的に`timed_out`にし、
reportを`agent_failed`へ戻して、再度Agentを走らせられる状態にします。いわば**掃除役**です。

4 tableすべてでRLSが有効、かつ**anon/authenticated向けのpolicyは1つも作りません**。

これは書き忘れではなく設計です。RLSは「policyが無ければ全部拒否」なので、
policyを1つも書かないことで「公開鍵（publishable key）でDBを直接叩いても何も見えない」状態になります。
DBに触れるのは、service role keyを持つEdge Functionsだけ。
**「全アクセスはEdge Function経由」という方針を、policyの不在によって物理的に保証している**わけです。

#### ② Edge Functions（5本）

| function | 呼ぶ人 | 認証 | 役割 |
| --- | --- | --- | --- |
| `create-report` | JavaFXアプリ | publishable key（`apikey` header） | 入力検査 → report行の作成 → 署名付きupload URLを返す |
| `finalize-report` | JavaFXアプリ | 同上 | 全artifactのsize/hash照合、redaction検査 → GitHub Issue作成 |
| `dispatcher-control` | dispatcher | `Bearer DISPATCHER_TOKEN` | claim / status更新 / redacted artifactの署名URL発行 |
| `get-redacted-artifacts` | dispatcher | 同上 | 黒塗り済みファイルとmanifestだけに、120秒有効の署名URLを発行 |
| `purge-expired-artifacts` | Cron | 同上 | 期限切れの**rawのみ**削除しeventを追記 |

**「report」とは**: 利用者がアプリから送る**不具合・改善の報告1件**です。
コメント本文、スクリーンショット、アプリのログ、環境情報がひとまとまりになっています。
DB上は `reports` tableの1行に対応します。

**「artifact」とは**: 報告に添付される**ファイル1つ**のことです（成果物・添付物）。
種類（`kind`）は次の5つで、**同じkindは1報告に1つまで**です。

| kind | 中身 | MIME type |
| --- | --- | --- |
| `rawScreenshot` | 加工前のスクリーンショット | `image/png` |
| `rawLog` | 加工前のアプリログ | `application/x-ndjson` |
| `redactedScreenshot` | 黒塗り済みスクリーンショット | `image/png` |
| `redactedLog` | 機微情報を除いたログ | `application/x-ndjson` |
| `manifest` | 上4つのSHA-256とbyte数を並べた目録 | `application/json` |

つまり「1〜5件」は**1件の報告に添付できるファイル数**であり、
**報告を5件まとめて受け付けるという意味ではありません**（1 requestにつき報告は1件）。
上限5は「5種類すべてが揃った状態」を指します。
なお1時間に受け付けられる報告の件数は別枠で10件です（rate limit）。

**「入力検査」とは**: 受け取ったJSONが想定どおりかを、DBに書く前に確認することです。
`create-report`では具体的に、idempotencyKeyがUUID形式か、categoryが4種のいずれか、
コメントが空でないか、artifactが1〜5件で重複が無いか、kindごとのMIME typeが上表と一致するか、
SHA-256が64桁の16進数か、1件が10MiBを超えていないか、を確認します
（該当するエラーコードは[3.6](#36-エラーコード早見表)）。

**「redacted artifact」とは**: **黒塗り済みのファイル**のことです（redact = 墨消しする）。
利用者が送るファイルには2種類あります。

- **raw**: 加工していない元のスクリーンショット/ログ。個人情報やsecretが写り込んでいる可能性がある
- **redacted**: 利用者が画面上で黒塗りし、ログからも機微情報を除いたもの

**Agentとdispatcherにはredactedしか渡しません。** rawはSupabase内に残り、30日後に自動削除されます。

**「redacted+manifestのみ120秒の署名URL」とは**: `get-redacted-artifacts`は、
その報告のファイルのうち `redactedScreenshot` / `redactedLog` / `manifest` の3種だけを選び、
**120秒で失効する使い捨てダウンロードURL**を発行する、という意味です。ポイントは3つあります。

1. **rawは対象外** — 種類で絞っているので、そもそもrawのURLは発行されません
2. **120秒で失効** — URLがログや画面に残っても、2分後には使えません
3. **manifest** — 各ファイルのSHA-256とbyte数を並べた目録ファイル。受け取った側が改竄されていないか照合するために一緒に渡します

#### ③ `config.toml`

local用の設定です。API port 54321、DB port 54322、Storage 10MiB、
5 functionすべて`verify_jwt = false`（＝ログイン済みユーザーのJWTを要求しない。
代わりに各functionが自前でkeyやtokenを検査します）。

## 3.1 CLIの用意とルートの選択

### CLIを入れる（Ubuntu）

Supabase CLIは**aptの公式リポジトリでは配布されていません**。またnpmでの
グローバル導入（`npm install -g supabase`）はサポート対象外で、実行するとエラーになります。
Ubuntuでは次の2通りのどちらかを使います。

**方法1（推奨）: GitHub Releasesの`.deb`を入れる**

```bash
scripts/install-supabase-cli.sh
```

版は**GitHubの最新releaseから解決**されます。architecture（`amd64` / `arm64`）は`dpkg`から判定します。
download後にbyte数とSHA-256を表示し、**確認に答えるまで`sudo`は実行しません**。

版を固定したい場合は引数か環境変数で渡します。何が取得されるかだけ見たい場合は`--dry-run`です。

```bash
scripts/install-supabase-cli.sh 2.113.0      # このリポジトリでの検証時の版（I-014）
scripts/install-supabase-cli.sh --dry-run    # URLを表示するだけ
```

手で入れる場合は次のとおりです。資産名は`supabase_<version>_linux_amd64.deb`の形式です。

```bash
VERSION=2.113.0
cd /tmp
curl -fsSLO "https://github.com/supabase/cli/releases/download/v${VERSION}/supabase_${VERSION}_linux_amd64.deb"
sudo dpkg -i "supabase_${VERSION}_linux_amd64.deb"
```

更新するときは新しい版の`.deb`を同じ手順で入れ直します。

**方法2: 入れずにnpxで都度実行する**

```bash
npx supabase@2.113.0 --version
```

この場合、以降のコマンドはすべて`supabase ...`を`npx supabase@2.113.0 ...`に読み替えてください。
Node.jsが必要です。

**導入できたら共通で次を実行します。**

```bash
supabase --version
supabase login          # access tokenでの認証（ブラウザが開きます）
```

`supabase login`はブラウザでSupabaseにログインし、CLIとアカウントを紐づけます。
tokenは`~/.supabase/`配下に保存されるため、以降は再認証不要です。
ブラウザが開けない環境ではDashboardの Account > Access Tokens で発行した値を
`supabase login --token <値>` で渡せます。

### どちらのルートで進めるか

| | ルートA: local | ルートB: cloud |
| --- | --- | --- |
| 動く場所 | 自分のPC上のDocker container | Supabaseのサーバー |
| 必要なもの | **Docker** | Supabaseアカウント（無料枠で可） |
| 外部通信 | 無し（GitHub Issue作成を除く） | あり |
| 用途 | 仕組みの確認、開発 | 本番相当の検証 |

**localスタック**とは、Postgres・Storage・Edge Functionsなど**Supabaseの構成要素一式を、
自分のPC上のDocker containerとして起動したもの**です。`supabase start` の1コマンドで立ち上がり、
cloudのprojectと同じAPIが `http://127.0.0.1:54321` に現れます。外部に何も送りません。

**この作業環境ではDocker socketへアクセスできず、localスタックは起動できていません**（`I-014`）。
理由はDockerが未インストールだからではなく、**socketファイルの権限**です。

`supabase start`はDocker daemonに`/var/run/docker.sock`というUNIX socket経由で指示を出します。
このファイルの所有者は`root`、グループは`docker`、権限は`srw-rw----`（660）です。
つまり**rootか、`docker`グループに属するユーザーしか読み書きできません**。
現在の作業ユーザーはこのグループに入っていないため、接続時に`permission denied`となります。
（`sudo`はpassword入力が必要で、非対話のAgent実行からは補えませんでした。）

自分の環境で確認・解消するには次のようにします。

```bash
ls -l /var/run/docker.sock     # → srw-rw---- 1 root docker ... なら権限方式は上記のとおり
id -nG | tr ' ' '\n' | grep -x docker   # 何も出なければ docker グループに未所属

# 解消（管理者権限が必要。実行後は一度ログアウト/ログインするか newgrp docker）
sudo usermod -aG docker "$USER"
newgrp docker
docker info                    # エラーなく情報が出れば OK
```

> `docker`グループへの追加は、実質的にroot相当の権限を与える操作です。
> 共用マシンや権限を持たない環境では無理に行わず、ルートBへ進んでください。

Dockerが使えない場合は[3.3 cloud project](#33-ルートb-cloud-project本番相当)へ進んでください。

## 3.2 ルートA: localで動かす

外部へ何も送らずに、Edge Functionsを含む一連の流れを確認できます。

**手順1: スタック起動**

```bash
supabase start
```

初回はcontainer imageのdownloadで数分かかります。
完了すると`API URL`（`http://127.0.0.1:54321`）、`DB URL`、`anon key` / `publishable key`、
`service_role key`が一覧で表示されるので、この値を控えます。
migrationは`supabase start`時に自動で適用されます。DBを初期状態に戻したいときは`supabase db reset`。

**手順2: functionsのsecretsを用意**

**secrets**とは、**Edge Functionsが実行時に読む秘密の設定値**のことです。実体は環境変数で、
function側は`Deno.env.get("DISPATCHER_TOKEN")`のように取り出します。
GitHubのtokenやservice role keyなど、**コードに直接書いてgitに入れてはいけない値**をここに置きます。

渡し方はlocalとcloudで異なります。

| | 置き場所 | 渡し方 |
| --- | --- | --- |
| local | `supabase/.env`（gitignore対象） | `supabase functions serve --env-file supabase/.env` |
| cloud | Supabase側に保管される | `supabase secrets set --env-file ...`（[3.3 手順5](#手順5-edge-secretsを設定する)） |

```bash
cp supabase/.env.example supabase/.env && chmod 600 supabase/.env
```

localでは次のように埋めます。

```
SUPABASE_URL=http://127.0.0.1:54321
SUPABASE_SERVICE_ROLE_KEY=<supabase startが表示したservice_role key>
GITHUB_APP_TOKEN=dummy-not-used-locally
GITHUB_REPOSITORY=owner/private-repository
DISPATCHER_TOKEN=<openssl rand -base64 48 の結果>
```

> `GITHUB_APP_TOKEN`にdummyを入れると、`finalize-report`はIssue作成の段階で失敗し、
> reportは`upload_failed`へ戻ってeventが積まれます。Issue作成まで確認したい場合は
> 実際のtokenと**捨ててよいテスト用repository**を指定してください。

**手順3: functionsを配信**

```bash
supabase functions serve --env-file supabase/.env
```

このコマンドは実行したまま（前面で待機したまま）にしておきます。別のターミナルで次へ進みます。

**手順4: アプリを繋ぐ**

```bash
export REPORT_API_URL='http://127.0.0.1:54321'
export SUPABASE_PUBLISHABLE_KEY='<supabase startが表示したpublishable/anon key>'
./gradlew :app:run
```

## 3.3 ルートB: cloud project（本番相当）

`dev-notes/operations.md`のprovisioning gatesに対応する手順です。

### 手順1: projectを作る

Supabase Dashboard（<https://supabase.com/dashboard>）で **New project** を押すと、次の画面になります。

![新規project作成画面](./png/creating-a-new-supabase-project.png)

上から順に、次のように入力します。

| 項目 | 入力内容 |
| --- | --- |
| **Organization** | 自分の組織を選ぶ（個人アカウントなら1つだけ表示されます） |
| **GitHub (optional)** | **接続しません。** これはschemaをGitHubからSupabaseへ自動反映する機能で、本プロジェクトはCLI（`scripts/deploy-supabase.sh`）から明示的にdeployする方針です |
| **Project name** | 任意。画像の例では `pfci` |
| **Database password** | 強いものを生成し、**安全な場所に保管**（`.env`には入れません）。`supabase db push`のときに聞かれます |
| **Region** | **Northeast Asia (Tokyo)** = `ap-northeast-1` を選ぶ |
| **Security** | 下記の3つのcheckboxを確認 |

Securityの3項目は、この設計では次のようにします。

- **Enable Data API** — **ONのまま**。Edge Functionsは`@supabase/supabase-js`経由でDBを読み書きしており、
  その通り道がこのData APIだからです。OFFにするとfunctionsが動きません。
  「公開APIをONにして大丈夫か」と不安になりますが、**RLSが有効でpolicyが1つも無いため、
  publishable keyで外から叩いても何も読めません**（[3.0](#このリポジトリがsupabaseに作るもの)参照）。
- **Automatically expose new tables** — **OFFを推奨**。
  新しく作ったtableを自動的にAPIへ公開する設定で、画面上でもSupabase自身が無効化を勧めています。
  本プロジェクトのtableはEdge Functions（service role）からしか触らないので、自動公開は不要です。
- **Enable automatic RLS** — どちらでも構いません。
  新規tableのRLSを自動で有効化する機能ですが、本プロジェクトのmigrationは
  4 tableすべてに対して`enable row level security`を自分で書いているためです。

**Create new project**を押すと、1〜2分で準備が終わります。

作成後のproject画面（project portal）はこうなります。

![project portal](./png/project-overview.png)

この画面で確認しておくものが2つあります。

- **project URL** — プロジェクト名の下に出ている `https://<project-ref>.supabase.co`。
  画像では `https://xuacnvdoaobxsgtxusqi.supabase.co`
- **project ref** — そのURLのサブドメイン部分（画像では `xuacnvdoaobxsgtxusqi`）。
  Project Settings > General の **Reference ID** と同じ値です。
  以降のCLI操作で `SUPABASE_PROJECT_REF` として使うので控えます

なお、この時点では **LAST MIGRATION: No migrations** と表示されています。
手順3を実行すると、ここにmigrationの適用日時が入ります。**進んだかどうかの確認に使えます。**

### 手順2: 鍵を控える

Project Overview から Project URL（`https://<ref>.supabase.co`）を控える。これは `REPORT_API_URL` に使う。

またProject Overviewの画面下の **Get connected > API Keys**（左sidebarの Project Settings > API Keys でも同じ）から、次を取得する。

| 取得するもの | 用途 |
| --- | --- |
| Publishable key（`sb_publishable_...`） | `SUPABASE_PUBLISHABLE_KEY`。アプリへ配布 |
| Service role key | Edge側のみ。**配布しない**。cloudでは自動注入されるため通常は控えるだけ |

![project portal](./png/project-settings-api-keys.png)

鍵の見分け方は[2.6 鍵の種類を見分ける](setup-env.md#26-鍵の種類を見分ける)にまとめてあります。

### 手順3: migrationとfunctionsを配置する

```bash
export SUPABASE_PROJECT_REF='<project-ref>'
scripts/deploy-supabase.sh
```

このscriptは `supabase link`（ローカルの作業dirとcloud projectを紐づける）
→ `supabase db push`（migrationのSQLを実行してtable/function/bucketを作る）
→ 5 functionの`deploy` を順に実行します。
`db push`は手順1で保管したDBパスワードを尋ねます。

完了後、project portalの **LAST MIGRATION** に日時が入り、
左sidebarのTable Editorに4 tableが見えていれば成功です。

### 手順4: GitHub Appを2つ用意する

**GitHub Appとは**: リポジトリではありません。
**GitHubに登録する「プログラム用のアカウント」**だと考えてください。
人間がIDとパスワードでログインするのと同じように、
プログラムがGitHub APIを操作するには身分と権限が要ります。それを与える仕組みがGitHub Appです。

- [GitHub](https://github.com/)上で「App」を作り、**Issueの読み書き**のように**必要な権限だけ**を選ぶ
- そのAppを対象のリポジトリに**install（インストール）**する
- Appは**installation token**という有効期限付きの鍵を発行できる。プログラムはこの鍵でAPIを叩く
- **Appに与えていない操作は、tokenを持っていても実行できない**

個人のPersonal Access Tokenは、うっかりすると自分のアカウント権限が丸ごと乗ってしまいますが、
GitHub Appなら**用途ごとに権限を絞った鍵を分けて発行できます**。だから2つ作ります。

Appの作成は [GitHub](https://github.com/) の <u>Settings > Developer settings > GitHub Apps</u>[^1] から行います。

[^1]: 

**この資料に出てくる「Edge」と「dispatcher」**（[3.0の用語ミニ辞典](#用語ミニ辞典)の再掲）:

| 呼び名 | 実体 | どこで動くか | GitHubに対して何をするか |
| --- | --- | --- | --- |
| **Edge**（Edge Functions） | Supabase上で動く小さなサーバープログラム。`create-report`など5本 | Supabaseのサーバー。URLでインターネットに公開されている | `finalize-report`が報告からIssueを**作る**だけ |
| **dispatcher** | このリポジトリの`:dispatcher` module。Issueを拾ってコーディングAgentを起動するbatch | 運用者が管理する専用Ubuntuサーバー（外から呼べない） | Issueを読み、labelとcommentを更新し、branchをpushしてdraft PRを作る |

ここで漏れる可能性を心配しているのは、リポジトリのパスワードではなく
**GitHub Appのinstallation token**（`GITHUB_APP_TOKEN`）です。
これはプログラムがGitHub APIを叩くための鍵で、**持っている人はそのAppに与えられた権限を全部使えます**。

Edge用のtokenは、**インターネットに公開されたEdge Functions**（`verify_jwt = false`＝誰でもURLを叩ける）
の中で使われるため、**閉じたサーバーの中にしか無い**dispatcher側のtokenより攻撃にさらされやすい位置にあります。
そこでEdge用Appには**Issueの作成/読み取りとmetadataしか与えません**。
こうしておけば、万一このtokenが漏れても、できるのはIssueを立てることまでで、
**コードのpush、PRのmerge、設定変更、Actionsの実行はいずれも不可能**です。
1つのAppに全権限をまとめてしまうと、この切り分けが効かなくなります。

| App | 使う人 | 与える権限 | 与えてはいけない権限 |
| --- | --- | --- | --- |
| Edge用 | Edge Functions（`finalize-report`） | Issue の作成/読み取り、metadata | それ以外すべて |
| dispatcher用 | dispatcher（専用サーバー） | Issue読み取り、label/comment書き込み、branch push、draft PR作成 | merge、administration、Actions write、environments、deployment |

dispatcher用ですらmerge権限を持たない点が重要です。**最終的なmergeは人間だけが行います。**

### 手順5: Edge secretsを設定する

Edge Functionsが使う秘密の値（GitHub tokenなど）をcloud側に登録します。
`GITHUB_APP_TOKEN`は手順4で作ったEdge用Appのinstallation tokenなので、先に手順4を済ませてください。

```bash
supabase secrets set --env-file supabase/.env --project-ref "$SUPABASE_PROJECT_REF"
supabase secrets list --project-ref "$SUPABASE_PROJECT_REF"
```

> **注意**: hostedのEdge Functionsでは`SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` /
> `SUPABASE_ANON_KEY` / `SUPABASE_DB_URL`が予約済みで自動注入され、`SUPABASE_`で始まる名前は
> secretsとして登録できません（CLIが拒否します）。その場合は`supabase/.env`から`SUPABASE_*`の2行を除いた
> ファイルを用意して`--env-file`に渡すか、3つを個別に設定してください。
> このリポジトリではcloudへのdeployをまだ実施していないため（`I-010`）、CLIの応答で必ず確認してください。

`--env-file`を使うのは、`supabase secrets set KEY=value`だとshellのhistoryに実値が残るためです。

必要な3つ:

| secret | 値 |
| --- | --- |
| `GITHUB_APP_TOKEN` | Edge用GitHub Appのinstallation token（手順4） |
| `GITHUB_REPOSITORY` | `owner/private-repository` |
| `DISPATCHER_TOKEN` | `openssl rand -base64 48` で生成した値。dispatcher側の`.env`と同じ値 |

### 手順6: repositoryのlabelとbranch保護

repository管理者として実行します（`gh`が認証済みであること）。

```bash
export GITHUB_REPOSITORY='owner/private-repository'
scripts/configure-github.sh
```

9種のlabel作成と、default branchの保護（required check `verify`、承認1件、stale review却下、
force push/削除禁止、管理者にも適用）を設定します。**実行後、GitHub UIで実際に反映されているか目視確認してください。**

**9種のlabelとは**: Issueに貼る付箋のことです。この仕組みでは、labelが**報告の進行状況そのもの**を表し、
dispatcherは「どのIssueを次に処理すべきか」をlabelで判断します。
（人間が`agent-ready`を貼るまでAgentは動きません。ここが人間による承認gateです。）

| label | 意味 | 誰が貼るか |
| --- | --- | --- |
| `user-report` | アプリから作られた利用者報告であることの目印 | Edge（`finalize-report`がIssue作成時に自動付与） |
| `triage` | 内容の確認待ち。上と同時に付く初期状態 | 同上 |
| `agent-ready` | **内容を確認し、Agentに着手させてよいと承認した** | 人間 |
| `agent:codex` | 担当させるAgentがCodex CLI | 人間 |
| `agent:claude` | 担当させるAgentがClaude Code | 人間 |
| `agent-running` | Agentが実行中（claim済み） | dispatcher |
| `needs-info` | 情報が足りず、人間の補足が必要 | dispatcher |
| `agent-failed` | 失敗またはtimeout。原因を直して`agent-ready`を貼り直す | dispatcher |
| `pr-opened` | draft PRができた。人間のreview待ち | dispatcher |

dispatcherは`agent-ready`と`agent:*`の**両方**が付いたIssueだけを拾い、
claimに成功した時点で`agent-ready`を外して`agent-running`に貼り替えます
（`GhSupabaseControlPlane.nextReady` / `claim`）。
Agentの種類を指定し忘れると、いつまでも処理されないので注意してください。

実際の定義は`scripts/configure-github.sh`の先頭行にあり、`gh label create --force`で作られるため、
再実行しても重複せず色だけ更新されます。

### 手順7: 保持期間のCronを登録する

`purge-expired-artifacts`（期限切れrawの削除）を1日1回、認証付きで呼びます。

ここでいう**token**は`DISPATCHER_TOKEN`です。
`purge-expired-artifacts`は他のfunctionと同じく`Authorization: Bearer <DISPATCHER_TOKEN>`を要求するので、
Cronから呼ぶときもこの値を添える必要があります。
つまり**「定期実行の設定の中に秘密の値を書く」**ことになるため、置き場所が問題になります。

tokenはVault（Supabaseの暗号化された秘密情報の保管庫）に保存し、
**SQL migrationへ直接書かないでください**。migrationファイルはgitに入るため、
一度書くとtokenがリポジトリの履歴に永久に残ります。
下の例では、SQL中に値を書く代わりに`vault.decrypted_secrets`から実行時に取り出しています。

```sql
-- 例: Supabase Cron。token はVaultから取得する形にする
select cron.schedule('purge-expired-artifacts', '0 18 * * *', $$
  select net.http_post(
    url := 'https://<project-ref>.supabase.co/functions/v1/purge-expired-artifacts',
    headers := jsonb_build_object('Authorization', 'Bearer ' || (select decrypted_secret from vault.decrypted_secrets where name = 'dispatcher_token')),
    body := '{}'::jsonb
  );
$$);
```

削除されるのは**rawのみ**です。redactedと計測metadataは自動削除されず、PoC終了時に運用者が手動で消します（`I-008`）。

## 3.4 疎通確認

①②は`scripts/verify-remote.sh`が自動で行います。

```bash
set -a; source .env; set +a
scripts/verify-remote.sh
```

これは`scripts/doctor.sh --only functions,storage-private,edge-secrets,dispatcher-auth --full`の
別名です。下記は、そこで何を確かめているかの説明です。手で追う必要はありませんが、
**失敗したときに何が起きているかを理解しておくとデバッグが早くなります**。

なお、doctorの既定では`dispatcher-control`に`recoverStale`を送りません。認証が通ったことは、
DBを変更しない未知のactionが`400 unknown_action`を返すことで確かめます。
下記①と同じく**DB到達まで**確かめるには`scripts/doctor.sh --full`を使ってください。

**① dispatcher tokenによる認証が正しく働いているか**

`dispatcher-control`は`Authorization: Bearer <DISPATCHER_TOKEN>`を持つ相手だけを通す関数です。
この確認では、**間違ったtokenが拒否されること**と、**正しいtokenが通ること**の両方を実際に叩いて確かめます。
片方だけでは不十分で、前者だけなら「単に壊れている」場合と区別できず、
後者だけなら「実は誰でも通る」状態を見逃します。
`$DISPATCHER_ENDPOINT`には`https://<project-ref>.supabase.co/functions/v1/dispatcher-control`を入れます。

```bash
# 誤ったtoken → 401
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  -H 'authorization: Bearer wrong' -H 'content-type: application/json' \
  -d '{"action":"recoverStale"}' "$DISPATCHER_ENDPOINT"

# 正しいtoken → 200 {"recovered":0}
curl -s -X POST -H "authorization: Bearer $DISPATCHER_TOKEN" \
  -H 'content-type: application/json' -d '{"action":"recoverStale"}' "$DISPATCHER_ENDPOINT"
```

ここで使っている`recoverStale`は、[3.0](#このリポジトリがsupabaseに作るもの)で説明した
「45分以上放置されたAgent実行を`timed_out`に片付ける」処理です。
応答の`recovered`は**そのとき片付けた件数**なので、`{"recovered":0}`は
**「放置されたrunは1件も無かった」**という意味になります。

作ったばかりのprojectにはAgent実行の記録自体が無いため、ここは必ず0です。
**0であること自体が目的ではなく、「認証を通り、DBの関数呼び出しまで到達して正常に応答が返った」
ことが確認できれば成功**です。

**② Storageが本当にprivateか**

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  "$REPORT_API_URL/storage/v1/object/public/user-reports/reports/x/raw/screenshot.png"
```

401/403（実装により400/404）になり、**本文が取得できない**ことを確認します。
ここで200が返ってbucketの中身が見えるなら、bucketがpublicになっているので設定を見直してください。

**③ アプリからの往復**

```bash
set -a; source .env; set +a
scripts/smoke-test-report.sh
```

画面でpreviewを確認して送信し、`送信しました: <Issue URL>`が出ること、
生成されたIssueに**生path、署名URL、secretが含まれていない**ことを目視確認してから`agent-ready`を付けます。

**④ 受け入れ確認一式**

`dev-notes/operations.md`のacceptance checks（冪等性、hash不一致時の停止、purgeの範囲、
credentialの非継承、CI失敗時のmerge不可など）を実施してください。ここが本番投入の判断材料です。

**冪等性（べきとうせい / idempotency）**とは、**同じ操作を何回繰り返しても、結果が1回実行したときと同じになる性質**です。

このシステムでは通信の切断や利用者の再送が起こりえます。冪等でなければ、
1件の報告に対してIssueが2つ3つと増えてしまいます。そこでアプリは報告ごとに
`idempotencyKey`というUUIDを1つ発行し、再送時も同じ値を送ります。
Edge Functionsはこのkeyで既存の報告を探し、見つかれば**新規作成せずに同じreportとIssueを返します**
（`reports.idempotency_key`にunique制約があるため、DBレベルでも二重作成できません）。
受け入れ確認では「同じkeyで2回送ってもIssueが1つのままか」を実際に確かめます。

他の項目も一言で言うと次のとおりです。

| 項目 | 確かめること |
| --- | --- |
| hash不一致時の停止 | ファイルを改竄するとfinalizeが`409`で止まり、Issueが作られないこと |
| purgeの範囲 | 期限切れで消えるのがrawだけで、redactedとmanifestが残ること |
| credentialの非継承 | Agentの子processに`GITHUB_APP_TOKEN`等が渡っていないこと |
| CI失敗時のmerge不可 | `verify`が落ちたPRをmergeできないこと |

## 3.5 送信が成功するまでに通る検査

`finalize-report`は次を**すべて**満たさないとIssueを作りません。挙動を理解しておくとデバッグが早くなります。

1. 宣言した全artifactがStorageに存在する（無ければ`409 upload_incomplete`）
2. 各artifactのbyte数とSHA-256が宣言どおり（不一致は`409 artifact_mismatch`）
3. `redactedLog`にsecret/email/session/接続文字列のパターンが**残っていない**
4. `redactedScreenshot`・`redactedLog`・`manifest`が揃い、manifestの`redactionStatus`が`APPROVED`
5. manifest内のhash集合が、requestで宣言したhash集合と完全一致
6. Issue本文にsecret、`token=`付きURL、`reports/.../raw/`が含まれない（`assertSafeIssue`）

同じ`idempotencyKey`で再送すると、同じreportとIssueが返ります（新規作成されません）。
`idempotencyKey`は報告1件ごとにアプリが発行するUUIDで、
通信が途中で切れて再送しても**Issueが二重に立たない**ようにするための識別子です。

## 3.6 エラーコード早見表

| HTTP / code | 出す場所 | 原因 | 対処 |
| --- | --- | --- | --- |
| `400 invalid_idempotency_key` | create | UUID形式でない | clientのbundle生成を確認 |
| `400 invalid_category` | create | bug/usability/request/other以外 | — |
| `400 invalid_comment` | create | 状況が空 | 入力必須 |
| `400 invalid_artifact` | create | kind/MIME/hash形式/重複が不正 | manifestとの整合を確認 |
| `413 artifact_too_large` | create | 1件が10MiB超 | 画像サイズを縮小 |
| `429 rate_limited` | create | 1時間に10件超 | 時間をおく。下記の注意も参照 |
| `409 upload_incomplete` | finalize | uploadが途中で失敗 | 同じidempotencyKeyで再送すればupload URLが再発行される |
| `409 artifact_mismatch` | finalize | size/hash不一致、manifest不整合 | bundleを作り直す |
| `409 redaction_review_required` | finalize | redactedにsecretが残る、`APPROVED`でない、artifact不足 | preview上で追加の黒塗りをしてから再送 |
| `409 finalize_in_progress` | finalize | 同時finalize | 待って再試行 |
| `502 finalize_failed` | finalize | GitHub API失敗など | secretsとApp権限を確認。reportは`upload_failed`に戻る |
| `401` | dispatcher-control ほか | **token不一致とは限らない** | 下記注意 |

> **`dispatcher-control`の401について**: このfunctionは`try`全体のcatchで一律401を返すため、
> tokenが正しくても内部エラー（RPC失敗、不正なaction名など）が401として見えます。
> tokenを疑う前に、Supabase Dashboardのfunction logs（左sidebar > Edge Functions > 該当function > Logs）で
> 実際の例外messageを確認してください。

> **rate limitのkeyについて**: 集計keyは`x-client-id` headerが無ければ`x-forwarded-for`です。
> JavaFXアプリは`x-client-id`を送らないため、**同じ出口IPの利用者全員で10件/時を共有**します。
> 社内NAT配下で複数人がテストすると簡単に429になります。

## 3.7 既知の不具合: `localPath`が返らない

**現状、cloud/localどちらでも「アプリからの送信」は失敗します。** 送信を試す前に修正が必要です。

- `supabase/functions/create-report/index.ts` は upload URL の応答で
  `localPath: path.split(\`/reports/${id}/\`)[1]` を計算しています。
- しかし`path`は`artifactPath()`が返す **先頭スラッシュ無し**の`reports/<id>/raw/screenshot.png`です。
  separatorが`/reports/<id>/`（先頭スラッシュあり）なので一致せず、`split`は元の文字列1要素を返し、
  `[1]`は`undefined`になります。
- 結果、JSONから`localPath`が欠落し、Javaの`RemoteReportClient.submit`（`app/.../RemoteReportClient.java:57`）で
  `bundleDirectory.resolve(null)`となりNullPointerExceptionになります。画面には`失敗: null`が出ます。
- 単体testは stub server 側で`localPath`を正しい値でハードコードしているため、この不具合を検出できていません
  （`app/src/test/java/.../RemoteReportClientTest.java`）。

修正はseparatorから先頭スラッシュを外すだけです（同ファイル内の2箇所、既存report用と新規report用）。

```ts
// 修正前
localPath: path.split(`/reports/${inserted.data.id}/`)[1]
// 修正後（例）
localPath: path.slice(`reports/${inserted.data.id}/`.length)
```

併せて、stubに依存しない形（`localPath`欠落時に明示的なエラーを出す等）でtestを補強することを勧めます。
